# 活动 TODO 的文档生命周期

## 问题

跨多轮 Agent 会话的探索事项如果只留在聊天、临时计划或零散设计文档中，后续维护者难以发现当前缺口；如果把所有设想永久堆在 README 或 AGENTS 中，又会让高可见文档逐渐失真。

## 根因

- 项目此前没有活动待办的统一目录和索引。
- 没有规定阶段性证据何时更新，也没有规定完成或取消后如何清理。
- 永久知识与尚待验证的假设混在一起，容易让 Agent 把探索结论误当作已实现能力。

## 方案

- 使用 `docs/todos/README.md` 作为唯一活动索引，一个独立问题对应一个 TODO 文件。
- 在 `AGENTS.md` 和 README 中提供入口，使 Agent 与人工维护者开始 non-trivial 工作前能够发现相关事项。
- 源码 ZIP 通过显式允许列表携带活动 TODO，保证包内 README 的入口有效；新增或删除 TODO 时同步构建清单及其测试。
- 每个可验证阶段记录日期、脱敏证据、结论和下一步，但禁止写入账号、认证材料、资源 ID、原始响应或 trace。
- 整个事项完成后，把长期结论迁入 design、lessons、README 或测试，然后删除 TODO 和索引项；取消或被替代的事项同样删除。

## 预防措施

- TODO 只允许使用 `待探索`、`探索中`、`阻塞`，不保留“已完成”墓地。
- 改变 TODO 基线、范围或优先级的代码和文档变更必须同步更新对应文件；新增或删除活动文件还要同步源码 ZIP 白名单。
- 评审时同时检查索引、活动文件和迁入的正式知识，避免孤儿链接或重复真相来源。
