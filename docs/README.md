# 文档治理

`docs/` 保存可长期维护的产品信息、设计约束、经验结论、用户验收说明和活动探索事项。本文件是文档入口；根目录 [README](../README.md) 仍是安装、配置和日常使用的首要入口。

## 目录职责

| 目录或文件 | 记录内容 | 更新时机 |
| --- | --- | --- |
| [product/](product/README.md) | 产品定位、目标用户、当前已交付能力和产品边界 | 用户可感知的能力、范围或安全承诺变化时 |
| [design/](design/) | 稳定的架构、领域模型、接口契约和实现约束 | 技术设计或长期接口契约变化时 |
| [lessons/](lessons/) | 已解决问题的根因、方案和预防措施 | 完成非平凡问题并形成可复用结论时 |
| [todos/](todos/README.md) | 仍在探索、验证或设计中的事项 | 开始、推进、完成、取消或替代探索事项时 |
| [acceptance_guide_zh.md](acceptance_guide_zh.md) | 分发包用户可执行的验收说明 | 安装、认证、工具使用或验收流程变化时 |

## 维护规则

1. 每份文档必须有明确职责，不重复维护同一事实：产品“当前能做什么”以 `product/` 为准；技术“为什么和如何约束”以 `design/` 为准；未完成工作以 `todos/` 为准。
2. 改变公开 MCP 工具、用户可见能力、支持范围或安全承诺时，同步更新产品信息、README 和受影响的设计文档；接口破坏性变更必须明确说明兼容影响。
3. 活动探索只能放在 `todos/`。完成后将可长期复用的结论迁入产品、设计、经验、README 或测试，再删除 TODO 及其索引项；不要把失效待办长期保留在正式文档中。
4. 文档不得记录 Client Secret、access/refresh token、邮箱、实际 Client ID、本机配置、OneNote 资源 ID、原始 Graph 响应、Page 正文或 Agent trace。示例必须使用脱敏占位符。
5. 文件名使用小写英文和下划线；目录入口统一命名为 `README.md`。链接使用相对路径，并在移动或删除文件时一并更新引用。
6. 需要随源码 ZIP 分发的文档，必须同步加入 `scripts/build_release.py` 的显式允许列表，并由 `tests/test_release.py` 覆盖；开发专用文档不应进入分发包。

## 变更检查

提交文档变更前，至少检查：链接是否有效、产品现状与“待实现”是否分开、没有敏感信息，以及受影响的发布清单和测试是否已同步。涉及代码或发布清单时，运行相应测试；纯文档变更至少执行 `git diff --check`。
